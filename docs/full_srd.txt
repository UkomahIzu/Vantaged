2.2 Architecture principles
# Principle Why / consequence
1 The API is the only door to the
database.
Web and mobile never query tables directly. All permission checks live in one place.
Prisma connects with full privileges, so Supabase row-level security does not
protect Prisma queries — the API must.
2 Two narrow exceptions use
Supabase directly
(a) file uploads/downloads via short-lived signed URLs issued by the API; (b)
Realtime private channels for chat and live updates, protected by RLS policies on
realtime.messages .
3 Business rules live in a pure
TypeScript package ( @bt/core )
State machines, progress maths and point rules are plain functions — easy to unit-
test and shared by API and (read-only) by apps.
4 Shared contracts ( @bt/contracts ) Zod schemas define every request and response once; web, mobile and API import
the same types.
5 Side eﬀects via an outbox Every state change writes a DomainEvent  in the same transaction. Notifications,
points, audit and timers are produced from events — nothing is lost if a provider is
down.
6 Time-based rules are data Reminders, deadlines and flags are rows in ScheduledJob , executed by a job
runner. Works on any host (cron, scheduled function, or pg_cron ).
7 Oﬀline-first mobile writes Mobile writes go into a local outbox with an idempotency key ( clientRequestId );
the server accepts each exactly once.
8 Records that prove things are
immutable
Submitted proof, plan versions, reviews, receipts, dispute evidence, ratings and
audit logs cannot be edited or deleted (enforced in the API and by database
triggers).

2.4 Request lifecycle
1. Client sends a request to /api/v1/...  with a Supabase access token (Authorization: Bearer ; the web app uses
the session cookie).
2. Middleware verifies the JWT, loads the User , memberships and device trust into a request context.
3. The handler validates input with the shared Zod schema.
4. The handler calls authorize(ctx, action, resource)  (Section 6). Denied → 403 .

4.3 Modelling rules
Rule Detail
IDs UUID everywhere. User.id  equals the Supabase Auth user id, so the JWT sub  maps
straight to the user.
Money Minor units (kobo / cents) in BigInt  fields ending in Minor . Never floats. Serialised as
strings in JSON. Currency is stored per project and copied onto each payment.
Weights Basis points ( weightBp , 10 000 = 100 %). Stage weights in a project must total exactly 10 000.
Dates Timestamps in UTC; planning dates ( startDate , targetEnd ) as DATE . Display converts to
the user's timezone.
Plan versions Each sent / accepted plan is stored as an immutable JSON snapshot  in PlanVersion . Live
Stage  and PaymentItem  rows are (re)generated from the accepted snapshot.
Idempotency Anything created oﬀline carries a unique clientRequestId  ( ProgressUpdate , CheckIn ,
Message ). Re-sending returns the existing row.
Media ownership MediaAsset  belongs to exactly one owner (update, message, receipt, evidence or review)
via nullable foreign keys; a database CHECK constraint enforces "exactly one".
Identity privacy NIN / passport numbers are never stored. identityHash  = HMAC-SHA256(secret, normalised
ID number) is unique, which enforces one Client Admin account per identity (FR-IDV-02)
without keeping the number.
History over deletion Bank accounts are superseded, not deleted; members are marked REMOVED ; projects are
completed or cancelled, never deleted.
v1.1 readiness contractType , PAUSED  / CANCELLED  statuses already exist; expense and materials tables
are added in v1.1.

5 Authentication & sessions
5.1 Approach
Supabase Auth handles sign-up, sign-in, OTP and sessions for both apps. BuildTrack's own tables hold everything
else (roles, memberships, verification).
Web: session in HTTP-only cookies via Supabase's server-side helpers for Next.js. Mobile: Supabase JS client with
tokens in the device's secure storage.
API: verifies the Supabase JWT on every request and builds the request context.
SMS OTP: Supabase's Send SMS Hook routes OTP messages to the SMS provider chosen later (via the SmsSender
adapter), so a Nigerian provider can be used even if Supabase has no built-in integration for it.
5.2 Requirements
ID Requirement PRD
SR-AUT-01 Sign-up collects full name, email and phone (E.164, default +234). Both are verified by OTP
before the account becomes active.
FR-ACC-01/02
SR-AUT-02 On first successful sign-in the API creates the User  row (id = auth id) and, depending on the
chosen path, a ClientAccount  + ClientMember(CLIENT_ADMIN)  or a Contractor  +
ContractorMember(DIRECTOR)  + Subscription(FREE_PROJECT) .
FR-ACC-01
SR-AUT-03 Every app install sends a stable deviceKey . An unknown device for that user requires an SMS
OTP step-up before protected actions; on success Device.trustedAt  is set.
FR-ACC-07
SR-AUT-04 Invited users (staﬀ, Client Reps) sign up through the invitation link; accepting creates the
membership with the invited role and marks the invitation ACCEPTED .
FR-ACC-03/04
SR-AUT-05 Removing a member sets status = REMOVED ; the API rejects their requests for that account
immediately (checked per request, not cached in the JWT).
FR-ACC-06
SR-AUT-06 Client Admin identity verification (NIN or passport + selfie) is performed through the
IdentityVerifier  adapter; only the result and identityHash  are stored. A duplicate hash
is rejected.
FR-IDV-01..03
SR-AUT-07 Platform Admins are flagged with User.isPlatformAdmin , must use a trusted device, and
every admin action is written to AuditLog .
FR-ADM-06
SR-AUT-08 Auth endpoints are rate-limited per phone, email and IP (OTP requests in particular). —

6 Authorisation
6.1 Model
Permissions are decided in code by one function, called by every handler:
authorize(ctx: RequestContext, action: Action, resource: { projectId?; contractorId?; clientAccountId?; … })
  → { allowed: true } | { allowed: false; reason: string }
It resolves the user's side and role for the resource, then applies the rule for the action. Rules are a table in @bt/core
that mirrors PRD Section 5.3, so the matrix and the code cannot drift apart (a unit test checks every row).
6.2 Scoping rules
Who Can reach a project when…
Client Admin project.clientAccountId  is their client account.
Client Rep Their client account owns the project and a ClientRepProject  row exists and the action's
module is in modules .
Director, Site Manager, Oﬀice
Coordinator
project.contractorId  is their company (all company projects).
Crew Member Their company owns the project and a ProjectAssignment  exists.
Share-link viewer A valid, unrevoked, unexpired token for that project; read-only; never payments, bank details
or chat.
Crew viewer link Like a share link, but requires a signed-in Crew Member of the same company.
Platform Admin Administrative endpoints only ( /api/v1/admin/* ); every access audited.

6.4 Database-level protection
RLS is enabled on every application table with no policies for the anon  and authenticated  roles, so even a leaked
anon key cannot read data through Supabase's auto-generated APIs. Prisma uses a privileged connection and is
unaﬀected.
Realtime: RLS policies on realtime.messages  allow joining a private topic only if the user belongs to it (Section
12.2).
Storage: buckets are private; no direct policies for clients — access only by API-issued signed URLs.

7 API design
One REST API under /api/v1 , served by Next.js route handlers and used identically by the web app, the mobile app

7.1 Conventions
Topic Rule
Style Resource-oriented REST with explicit action endpoints for state changes (e.g. POST
/stages/{id}/submit ) instead of generic PATCHes, so every transition is validated and audited.
Format JSON. BigInt  money as strings; timestamps ISO 8601 UTC; enums as upper-case strings.
Validation Every body, query and response has a Zod schema in @bt/contracts ; invalid input → 400
VALIDATION_FAILED  with field errors.
Auth Authorization: Bearer <supabase access token>  (mobile) or session cookie (web). Public
endpoints are marked.
Idempotency Create endpoints used oﬀline accept a clientRequestId . Other POSTs accept an optional
Idempotency-Key  header.
Pagination Cursor-based: ?cursor=&limit=  (default 30, max 100); responses include nextCursor .
Concurrency State-changing actions check the current state inside the transaction; a stale action returns 409
INVALID_STATE  with the current state.
Errors { "error": { "code": "…", "message": "…", "details": {…} } }  — codes in Appendix D.
Versioning /v1  prefix. Breaking changes go to /v2 ; the mobile app sends X-App-Version  so old builds can
be told to update.
Rate limits Per user and per IP; stricter on auth, OTP, invitations and uploads.

9 Proof & media pipeline
9.1 Capture (mobile)
In-app camera for photos and video; microphone for voice notes. Each capture records: device time, GPS
latitude/longitude/accuracy (if permission given), uploader, and capturedInApp = true .
Gallery picks are allowed but saved with capturedInApp = false ; the UI labels them "Not captured in app" and
they do not count toward minimum proof.
Video recording stops automatically at 60 seconds; longer gallery videos are rejected client-side and server-side.
9.2 Processing
Type On-device processing before upload
Photo Resize to max 1920 px long edge, JPEG ~0.75 quality, strip EXIF except orientation; GPS/time kept in
metadata sent to the API (not in the file).
Video Transcode to 720p H.264, ≤ 60 s; target ≤ ~15 MB.
Voice AAC mono; ≤ 5 minutes.
Document PDF / image receipts ≤ 10 MB.
A SHA-256 hash is computed on device and re-checked on the server; it is stored on MediaAsset.sha256  as tamper
evidence.
9.3 Geofence
Each project has a pin and siteRadiusM  (default 200 m, editable by the contractor). The server computes withinSite
from the capture GPS (distance ≤ radius + accuracy). Media captured outside the site is flagged to the reviewer (FR-PRF-
03); check-ins outside the site do not count (FR-TSK-03). No GPS → withinSite = null , shown as "No location".
9.4 Upload flow
1. App asks POST /media/upload-urls  with file metadata (kind, size, duration, hash, capture data, owner type). API
checks permission and limits, creates MediaAsset(PENDING)  rows and returns signed upload URLs (short expiry).
2. App uploads files directly to Supabase Storage (resumable for video), in the background, retrying on failure.
3. App calls the owning endpoint (e.g. POST /projects/{id}/updates ) with the media ids; the API verifies each object
exists and its size/hash match, then marks UPLOADED .
4. Viewing uses short-lived signed download URLs (thumbnails cached on device).
9.5 Minimum-proof check
countedPhotos = media where kind=PHOTO and capturedInApp and uploadStatus=UPLOADED and update.stageId=stage.id
countedVideos = same for VIDEO
canSubmit = checklist.every(done) && countedPhotos ≥ stage.minPhotos && countedVideos ≥ stage.minVideos
            && (!stage.requireDescription || some update has a description)

10.3 Oﬀline architecture
Part Design
Local store SQLite database holding the user's projects, stages, checklist, tasks, recent updates and chat (read

Outbox Every oﬀline-capable write (update, checklist tick, task completion, check-in, chat message) is saved

the UI as "Waiting to sync".
Sync push When online, media are uploaded first (Section 9.4), then operations are sent in order via POST
/sync/push . The server applies each once (idempotent) and returns per-item results; failures are
shown to the user with a reason (e.g. "stage already submitted").
Sync pull GET /sync/pull?since=cursor  returns changes for the user's projects; also triggered by realtime
"project changed" signals and on app foreground.

stores both capturedAt  and createdAt .
Conflicts Server state wins for transitions (submit, approve, confirm); these actions require a connection.

12 Chat & realtime
12.1 Design
Every conversation belongs to exactly one contractor company (Conversation.contractorId ), which keeps chat
"contained within the company and its clients" (FR-CHT).
Types: COMPANY_DIRECT  and COMPANY_GROUP  (staﬀ only) and PROJECT  (the project's client side + contractor staﬀ,
created automatically when a client connects).
Writes go through the API (POST /conversations/{id}/messages , idempotent), which saves the message, then
publishes it on the conversation's Realtime channel.
Reads: clients subscribe to private Realtime channels for live delivery and use the API for history.
Participants who leave (removed staﬀ) keep no access; their past messages stay (FR-CHT-05).
Crew Members see company chats they are added to; they have no project chat with the client by default (PRD 5.3).
12.2 Channel security
Channel topic Who may join (RLS policy on realtime.messages )
conv:{conversationId} Users with an active ConversationParticipant  row.
project:{projectId} Users who can reach the project (Section 6.2); used for "project changed" signals
only — no sensitive data in the payload.
user:{userId} That user only; new notifications, unread counts.
Channels are created with private: true ; policies use realtime.topic()  and the JWT sub  to check membership.
Because policies are cached for the connection, removing a participant also forces a token refresh / disconnect for that
user.
12.3 Features
Text, photos, videos (≤ 60 s), documents, voice notes; delivery and read state from lastReadAt ; oﬀline sending through
the outbox; unread counts per conversation; in-context comments via the Comment  model on stages, updates, issues,
payments and change requests.
